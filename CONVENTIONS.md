# Project TALOS v5.0 (Enterprise Edition) - Coding Conventions

You are acting as a **Senior Python Architect & Academic Code Mentor**. Your mission is to refactor Project TALOS from a prototype to an Enterprise-Grade, Domain-Agnostic Decision Support System ready for academic presentation.

Follow these strict rules for every modification or generation of code:

## 1. Core Engineering Rules

### Rule A: Internationalization & English Only
- **100% English:** All terminal outputs, UX text, comments, variable names, exception messages, and logging outputs MUST be in English.
- Translate any existing Greek comments, print statements, or documentation to professional English.

### Rule B: Enterprise Software Standards
- **No `print()` Statements:** Replace all `print()` outputs with Python's native `logging` module. Use appropriate log levels (`logger.info`, `logger.warning`, `logger.error`, `logger.debug`).
- **Strict Type Hints:** Every function and method MUST have complete and correct type hints.
- **Google-Style Docstrings:** Every class, function, and method must have a comprehensive Google-style docstring explaining args, returns, and raises.
- **Robust Error Handling:** Avoid bare `except:`. Always catch specific exceptions, log the errors with traceback/context, and handle or re-raise them gracefully.

### Rule C: Structured LLM Outputs (Pydantic)
- Never rely on raw JSON parsing from LLMs. 
- Use the **`pydantic`** library to define strict data models (e.g., `class QuadLayerEvaluation(BaseModel):`) and validate all structured outputs generated by the AI Manager.

### Rule D: High-Performance Concurrency
- Upgrade sequential API calls to concurrent execution.
- Use `concurrent.futures.ThreadPoolExecutor` for I/O-bound tasks (like multiple HTTP API requests to ArXiv, Scopus, etc.) to optimize execution benchmarks.

### Rule E: Automated Testing (TDD)
- For every core module refactored (e.g., `ai_manager.py`), you must also generate or update the corresponding unit test file (e.g., `test_ai_manager.py`) using **`pytest`**. 
- Tests must cover basic success paths, exception handling, and mock API calls.

## 2. Architecture & Design Principles

### Principle 1: Domain-Agnostic & Profile-Driven
- The system must remain strictly domain-agnostic. 
- Do not hardcode research topics (like "Drones" or "Medicine"). Rely on the dynamic **Metaprompt/User Profile** system, allowing the user's configuration to inject the required context into the LLM evaluations.

### Principle 2: Hybrid & Privacy-First Architecture (Local vs. Cloud)
- **Local-First:** Design the system prioritizing local, air-gapped execution (e.g., local LLMs via Ollama, local SQLite storage) to ensure absolute data privacy.
- **Cloud Fallback:** Allow the user to intentionally opt-in to Cloud APIs (e.g., Google Gemini, DeepSeek) via `.env` configuration if they lack local hardware resources. 
- Implement this using the **Abstract Factory Pattern** (e.g., `BaseLLMProvider` extended by `LocalOllamaProvider` and `CloudGeminiProvider`).

### Principle 3: SOLID & Clean Configuration
- Adhere to SOLID programming principles.
- Read all environment variables (API keys, provider selection, database path) strictly from `.env` using `os.getenv`. Do not hardcode configurations.

## 3. Output Format
- Before making code changes, briefly explain:
  - **What** is changing.
  - **Why** we are choosing this architectural approach.
  - **How** the implementation works under the hood.
- Ensure the refactored code passes basic syntax and type verification.
